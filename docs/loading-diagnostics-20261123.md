# 최초 로딩 실패 진단

## 구현과 보존

기존 최초 로딩의 실패·재시도 처리는 유지하고 진단만 추가했습니다. location, scene-data, image-assets, shared-models, scene-build, ready 여섯 단계의 시간과 이미지/데이터 실패·재시도 회복을 기록합니다. HTTP 응답, JSON 문법 오류와 응답 본문 전송 실패를 구분하며, 브라우저가 제공하는 ResourceTiming 상태·크기를 해당 시도에 연결합니다.

진단은 sessionStorage의 neighborhood-loading-diagnostics-v1에 최근3세션, 세션당80이벤트, 총24KiB 이내로 남습니다. 탭을 닫으면 없어집니다. 고정 자산 파일명·숫자·허용 분류만 저장하고 주소·좌표·장면ID·URL·인증키·임의 오류문구는 저장하거나 외부로 전송하지 않습니다. 진단 저장 실패는 본래 로딩을 막지 않습니다. 정상 자원마다 저장하지 않고 단계·실패·회복·종료 때 기록합니다.

읽기: 개발자 진단에서 `JSON.parse(sessionStorage.getItem('neighborhood-loading-diagnostics-v1') || '[]')`. 저장소 접근이 막힌 경우 같은 모듈의 loadingDiagnostics.read()가 제한된 메모리 기록을 반환합니다. 기록은 실제 장면 데이터나 설정을 바꾸지 않습니다.

선택 소스2f3f33ca59000c70e5ed31c36cb7b71530ea20af의14개 파일만 커밋했습니다. 다른 대화의20개 변경 및 staged13개 원문은 보존했습니다. 필수 검사36개 및 공개 빌드1602개 파일/956.7MB가 통과했습니다.

## 해석 기준

[Resource Timing 표준](https://www.w3.org/TR/resource-timing/)에 따라 일부 정책 차단은 timing 자체가 없을 수 있습니다. timing 없음·상태0·온라인 표시만으로 원인을 확정하지 않습니다. [transferSize 설명](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/transferSize)의 제약에 따라 전송크기0만으로 캐시 적중도 판단하지 않습니다. 기록에 없는 정보는 미확정으로 남깁니다.

## 공개 배포와 재현

첫 공개 소스 2f3f33c와 호스팅 7774d9c의 배포 후 공개 파일10개가 clean build와 일치했습니다. 같은 저장 장면의 캐시 비활성 새 문서3회 중2회는39.243초/31.338초에 완료했고,3회째는 scene-build 중 Edge renderer가 종료됐습니다. 마지막 기록은 추적 성공62/실패0이며, 이미지 단계는 통과했습니다. 오류 코드5만으로 메모리·GPU·브라우저 원인을 구분할 수 없습니다. 새로 고침 후13.947초에 정상 복구됐고 이전 running 기록도 남았습니다. 내부 충돌 페이지는 브라우저 도구의 URL 보안 정책으로 접근하지 못했습니다.

HTTP404 두 번과 HTTP200 손상 이미지 두 번을 각각 주입하면 지정 이미지 파일명, image-event, 두 번의 시도, final-error가 기록되고 실패 안내가 표시됐습니다. 최초404 후 실제 이미지를 허용한 경우 recovered가 기록됐으며53.005초에 ready/성공69/실패1로 완료했습니다. 이 시간은 수동 응답 주입 대기를 포함하므로 일반 로딩 성능으로 비교하지 않습니다. 통제한 실패는 과거 최초 실패의 원인을 소급 입증하지 않습니다.

초기 시험에서 timing=null이며 전역 resource 목록에도 대상 entry가 없었습니다. 검토 과정에서 observer가 error보다 먼저 전달되고 전역 버퍼에는 entry가 없는 경우 진단이 timing을 놓치는 조건을 재현했습니다. 제한된 token 안에 정제된 timing 한 개를 먼저 보관하도록 두 지점을 수정하고,404 실패와200 회복에 올바르게 연결되는 회귀 검사를 추가했습니다. 이는 진단 누락 수정이며 원래 로딩 실패 원인에 대한 증명은 아닙니다.

최종 소스 e8672a08461b2d0e2d47cb9e87884149a06215e3와 호스팅 8a26caef800a6610bf73a709d6c764f0a356a8aa의 CI·공개 배포가 성공했습니다. 수정 후 필수36검사와 전체 공개빌드도 다시 통과했고, 공개 파일10개가 검사한 build와 같았습니다. 호스팅의 다른 앱 루트도 바뀌지 않았습니다.

최종404 시험에서 resource 목록250개 상태에서도 별도 observer가404 두 개를 받았고 수정 진단에도 두 시도의404/9바이트가 남았습니다. HTTP200 손상 이미지도 두 시도 모두200/9바이트/image-event로 남아 두 조건을 구분했습니다. 초기 null의 모든 실행 순서를 소급 확정하지는 않지만, 전역 버퍼 없이 먼저 전달된 timing을 보존하는 수정 효과는 단위 재현과 공개 시험에서 확인됐습니다.

실패 주입을 해제한 최종 캐시 비활성 새 문서는28.315초에 ready, 추적 성공69/실패0, 콘솔 오류0으로 완료했습니다. 실제3D 장면과 설정 화면을 확인했고 캐시 override와 요청 가로채기를 해제했습니다. public-final.jpg와 public-final.json이 최종 화면·기록입니다.

## 남은 미확정 항목

원래 한 번 발생했던 이미지 Event의 실제 요청/응답은 당시 기록이 없어 원인을 확정하지 못했습니다. 이번 캐시 없는 정상 시험에서도 동일 이미지 실패는 자연 재현되지 않았습니다. 별도로 한 번 재현된 renderer 종료는 scene-build까지 범위를 좁혔지만 정확한 연산·GPU/메모리/브라우저 원인은 미확정입니다. 추측에 따른 렌더링 정책 변경은 적용하지 않았습니다. 따라서 진단 구현·검사·배포·공개 화면 확인은 완료됐지만, 최초 실패의 근본 원인 해결 완료를 뜻하지 않습니다.
